# ADR 0001 · Per-user authentication

- **Status:** Proposed (Phase 1). This **deviates from the planned library**; the reviewer either accepts the
  deviation or keeps Auth.js v5 (the fallback below). Both are written so Phase 3 can start on either.
- **Date:** 28/10/2026
- **Context sources:** `docs/BUILD-SPEC.md` §5.4 and §6 Phase 3; Phase 0 audit §3 and S1–S3, S19, S21.

## Context

Today there is one shared password (`DOSSIER_PASSWORD`, `src/lib/env.ts:31`) and a stateless JWE session
cookie with no user id (`src/lib/auth/session.ts:27-32`, `:65`). BUILD-SPEC §5.4 needs:

- per-user accounts, with verification, sign-in/out, and disable/delete;
- session expiry and **revocation**;
- secure cookies, CSRF protection and rate limits;
- no enumeration;
- no shared production password;
- no hand-rolled token crypto.

The project plan named **Auth.js (NextAuth v5)** with Google sign-in, an email magic link and the Prisma
adapter, "unless Phase 0 finds a blocker". Passwordless sign-in removes password storage and password reset
from scope.

## Finding that changes the plan

On 22 Sep 2025 Auth.js became part of Better Auth. The maintainers say they will "keep addressing security
patches and urgent issues". For new projects they write: "we strongly recommend new projects to start with
Better Auth unless there are some very specific feature gaps." The gap they name is stateless sessions
without a database, which we do not need.
Sources: https://www.better-auth.com/blog/authjs-joins-better-auth ·
https://github.com/nextauthjs/next-auth/discussions/13252

This is not a hard blocker: Auth.js v5 still works and still gets security fixes. But this product is new,
public and multi-user, and auth is its longest-lived dependency. Starting on a library in security-only
maintenance means a second migration later. Treat that as the blocker the plan allowed for.

## Decision

Use **Better Auth**, with:

- **Prisma adapter.** `prismaAdapter(prisma, { provider: "postgresql" })` from `better-auth/adapters/prisma`.
  Prisma's own Next.js guide uses `@prisma/client@7` + `@prisma/adapter-pg`, the same as this repo.
  https://www.prisma.io/docs/guides/authentication/better-auth/nextjs
- **Route.** `src/app/api/auth/[...all]/route.ts` exporting `toNextJsHandler(auth)` from `better-auth/next-js`
  (same guide).
- **Google sign-in.** `socialProviders.google { clientId, clientSecret }`
  (https://better-auth.com/docs/basic-usage). Sign-in asks only for basic profile and email scopes. The
  existing Gmail/Calendar integration keeps its own separate OAuth grant (`src/lib/google/*`), which stays
  off in V1.
- **Email magic link.** The `magicLink` plugin from `better-auth/plugins`, with
  `sendMagicLink({ email, url, token })`. Its default `expiresIn` is 300 s; we keep it. `disableSignUp` stays
  available for invite-only beta (https://better-auth.com/docs/plugins/magic-link).
- **Email delivery.** SMTP from the business mailbox the operator already has, so there is no new vendor,
  sent with `nodemailer`. The host and credentials are env vars set on the server (names in Phase 3 PR 1);
  the mailbox's SMTP limits are not checked yet. If SMTP is unavailable, Google sign-in alone is enough for
  the invite-only beta.
- **Sessions.** Database sessions, which gives revocation, "sign out everywhere" and account disable.
  Reading on the server uses `auth.api.getSession({ headers: await headers() })` (basic-usage page). Upstream's
  `getSession()` / `verifySession()` / `action()` / `route()` keep their names and call sites, but return
  `{ userId, … }`. That way the 20 action files and 16 routes change only where they use the identity.
- **Invite-only beta (the project's default).** An allowlist of emails, checked in a sign-up hook. Sign-up
  stays closed otherwise.
- **Rate limits.** Keep upstream's per-IP throttle for the sign-in endpoints, and add a per-email bucket for
  magic-link sends. The global `"*"` bucket (`src/lib/auth/login-throttle.ts:11`) is removed in multi-user
  mode, because one attacker could otherwise slow sign-in for everyone.
- **Single-password mode** stays only behind `DOSSIER_AUTH_MODE=single-password`, for local development and
  until cutover. In multi-user mode, start-up **refuses to boot** if `DOSSIER_PASSWORD` is set while
  `NODE_ENV=production`, so the shared password cannot linger.
- **Claude connector** (`src/lib/connector/oauth.ts:83-85`). Its tokens are bound to the password
  fingerprint today. In multi-user mode they carry `userId` plus a per-user generation stamp. The connector
  stays **off** in V1 until Phase 7.

Account linking (one person using both Google and a magic link with the same email) must be configured
explicitly. The exact Better Auth option is to be verified against its docs in Phase 3 PR 1; it is not
assumed here.

## Fallback: Auth.js v5 (if the reviewer rejects the deviation)

Same shape:

- Google provider plus an email provider, Resend or Nodemailer
  (https://authjs.dev/getting-started/authentication/email). It needs a database adapter: "It is not
  possible to enable an email provider without using a database".
- `@auth/prisma-adapter`, database sessions, and the same allowlist, throttle and boot guard.

## Not verified here

- Better Auth with **Next.js 16.3** (`src/proxy.ts`, Next's renamed middleware) and React 19.3. Phase 3 PR 1
  starts with a sign-in spike and pastes the result. If it fails, we fall back to Auth.js v5.
- The exact Prisma models the adapter generates: `User`, `Session`, `Account`, `Verification` per its
  schema generator. Phase 3 PR 1 records them in the migration.

## Consequences

- New tables: `User`, `Session`, `Account`, `Verification`. Every owned model gets `userId` (ADR 0002).
- Exit: both libraries store users and accounts in our Postgres, so switching later is a data migration,
  not a lock-in.
