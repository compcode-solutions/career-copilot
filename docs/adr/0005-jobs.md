# ADR 0005 · Background jobs: one instance, no queue service

- **Status:** Proposed (Phase 1)
- **Date:** 28/10/2026
- **Context sources:** `docs/BUILD-SPEC.md` §5.7; Phase 0 audit §7 and S11, S12, S20.

## Context

Upstream runs everything in the app process:

- the job queue on `globalThis` (`src/lib/jobs/runner.ts:70-71`), with concurrency set by the provider
  (`:198`);
- SSE progress (`:165`);
- timers for the job sweep, nightly backup, inbox sync, job agent and startups refresh
  (`src/instrumentation.ts:13-31`).

Upstream supports one instance only (`README.md:129`). Jobs have no owner (`prisma/schema.prisma:908`).
The beta is small (invite-only), and the VPS has one app container with 1 GB.

## Decision

- **One app instance**, as now (BUILD-SPEC §5.7). No Redis, no queue service, no new vendor. The deploy
  compose already runs a single `app`.
- **Owner on every job.** `Job.userId` is required (ADR 0002). `startJob()` takes `ctx` and stores
  `userId`. Handlers get `forUser(job.userId)` in their `JobContext`, never the raw client.
  `getJob` / `findLatestJob` / `findUnfinishedJobs` / `cancelJob` / `retryJob` take the caller's `userId`.
  The `jobs/[id]` and `jobs/[id]/events` routes therefore return 404 for another user's job.
- **Fairness.**
  - Keep the global concurrency limit.
  - Add a per-user limit of **2 running jobs**, with the rest queued in order, so one user's batch cannot
    starve the others.
  - Job `key`s become user-scoped (`user:<id>:application:<id>`).
  - Each scheduled per-user run gets an idempotency key `(userId, type, day)`, kept in a unique index, so a
    restart or double timer cannot run it twice.
- **Schedules become loops over users:**
  - **Job agent.** Each day, for each user with the agent on, enqueue one scan (counts against ADR 0004).
    It stays **off** in V1 until BUILD-SPEC Phase 6/7, per §5.7: "do not enable daily agent tasks until
    scheduling is durable, ownership-aware and resistant to duplicate execution".
  - **Inbox sync.** Per connected `GoogleAccount`. Off in V1 (Google integrations are off by default).
  - **Startups refresh** and the **job sweep.** Per user, or global where the rows are owner-scoped anyway.
  - **Nightly JSON backup.** Off in multi-user mode (ADR 0003). The host `pg_dump` replaces it.
- **Durability.** Job rows are already in Postgres, and `recoverInterruptedJobs()`
  (`src/instrumentation.ts:11`) re-queues or fails them after a restart. We keep that. Timers recompute
  their next run from the database on start (as `scheduledRunDue` does, `src/lib/agent/schedule.ts:33`),
  so a restart neither skips nor doubles a day.
- **PDF rendering** stays in-process with upstream's cap of two concurrent renders (`README.md`
  Performance). It is counted in the same per-user limit when started through a job.

## Exit (when one instance is not enough)

Move job claiming to Postgres: `UPDATE … WHERE id = (SELECT id FROM "Job" WHERE status = 'QUEUED' ORDER BY
createdAt FOR UPDATE SKIP LOCKED LIMIT 1)`. Move timer ownership to a Postgres advisory lock held by one
instance. Swap SSE fan-out to `LISTEN/NOTIFY`. All of this stays in the same database, still with no new
service. Not needed for the beta.
